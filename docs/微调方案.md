# 微调对照实验方案（LoRA / QLoRA）

> 目的：把「提示词 + 工程约束」这条主线和「参数高效微调」这条补充线合成一套可写进论文的实验设计。
> 所有数字都是本机实测或本仓库已有产物，不做估算性承诺。

## 0 一句话设计

**同一批 20 篇人工标注、同一套评测脚本、同一套后处理**，横向比较四个臂：

| 臂 | 模型 | 方法 | 状态 |
|---|---|---|---|
| A1 | qwen2.5:7b-instruct | 本体约束提示词（p1） | **已完成**：实体严格 F1 **0.784**、关系严格 F1 **0.555**（证据过滤后 0.597） |
| A2 | Qwen2.5-3B-Instruct | 同样的 p1 提示词 | 待跑（20 篇，约 15 分钟） |
| A3 | Qwen2.5-3B-Instruct | p1 弱标注 → QLoRA | 本方案主体 |
| A4（可选） | qwen2.5:7b-instruct | p1 弱标注 → QLoRA | 仅在本机空间/显存允许时做，否则写入局限 |

要回答的问题只有一个：**同规模模型上，「喂示例/改参数」与「改提示词」哪个更划算；小模型微调能不能逼近大模型提示词的结果。**

## 1 硬约束（全部实测，不是假设）

| 项目 | 实测值 | 影响 |
|---|---|---|
| GPU | RTX 3060 Laptop，**6144 MiB**，空闲时已占 **2112 MiB**（桌面/浏览器） | 训练可用约 3.5–4 GB |
| 驱动 | 566.07（CUDA 12.6 能力） | 必须装 cu124 轮子，不能装 cu118 以下 |
| C 盘可用 | **23.9 GB** / 475.3 GB | 7B fp16 权重要 15.2 GB，装完只剩 8 GB，风险高 |
| huggingface.co | **超时不通** | 必须 `HF_ENDPOINT=https://hf-mirror.com`（实测 200，1.2 s） |
| pypi.org / download.pytorch.org | 通（200，0.3–0.7 s） | torch 可直接装 |
| 项目 venv | Python 3.12.0，**无** torch/transformers/peft/bitsandbytes/datasets/accelerate/trl | 需新增依赖，体积约 3–4 GB |
| Ollama | 当前无模型常驻 | 训练前仍需 `ollama stop` 确保显存让出 |

**结论：训练 7B 的 QLoRA 在本机不现实**（4 GB 可用显存 + 剩 8 GB 磁盘）。方案主体用 **Qwen2.5-3B-Instruct**（fp16 权重约 6.2 GB，4-bit 训练显存约 2.5–3 GB），把 7B 作为「可选加做」。

## 2 数据：从已有产物蒸馏，不新标一个字

1. **弱标注生成**：用 A1 的提示词在**训练集 100 篇**上跑一遍 `src/llm/runner.py`（split=train），得到 raw 输出。按 A1 在 dev 上的实测速度（约 70 s/篇）预计 **100–120 分钟**，放后台跑。
   - 注意：只能用 train 100 篇。dev 里有 20 篇是评测集，碰了就是泄漏。
2. **过校验层**（`src/llm/postprocess.py` 已有，直接复用）：JSON 合法 → schema 通过 → 实体原文必须能在正文中找到 → 关系名别名归一 → 事故挂载修复 → 证据一致性 ≥ 0.85。
   - A1 在 dev 上的通过率实测：JSON 合法 100%、schema 通过 87.9%、证据命中 66.2%。按此估计 100 篇最终可用 **60–75 篇**。
3. **构造指令样本**：一条样本 = 文件头（`### 事故编号` 等元数据，与推理时一致）+ 正文片段（截断到 2048 token，按 `src/prep/segment.py` 的「原因 40% 优先」预算切）+ 目标输出（校验后的 JSON）。
   - 长文档按 2 段切，预计样本量 **100–150 条**。这个量级只够「格式与字段习惯对齐」，**不足以注入领域知识**——论文必须这样表述，这也是本实验的诚实边界。
4. **不做的两件事**：不做 p2 少样本再微调（会和提示词实验混淆）；不在 dev/test 上做任何训练或早停（早停只看训练损失）。

## 3 训练配置（3B / 4-bit QLoRA）

```
base            Qwen2.5-3B-Instruct（bf16 下载，bitsandbytes 4-bit NF4 加载，双重量化）
LoRA            r=32, alpha=64, dropout=0.05
target_modules  q_proj k_proj v_proj o_proj gate_proj up_proj down_proj
lr              2e-4（cosine，warmup 3%）   epochs 4   batch 1   grad_accum 8
max_seq_len     2048（正文截断 + 输出 JSON；输出侧保留完整结构）
其他            gradient_checkpointing=True, paged_adamw_8bit, bf16=True, seed=42
显存预算        权重 ~2.2 GB + 激活（2048 tok，checkpointing）~1.0 GB + 优化器 ~0.3 GB ≈ 3.5 GB
```

**偏差声明**：训练输入截断到 2048 token，而评测输入是 12000 字符（约 3000–3500 token）。这个不一致必须写进论文，并在 §6 的消融里用 1024 / 2048 两档看影响；不能默认忽略。

## 4 评测协议（与主实验完全对齐，杜绝「换个口径就涨点」）

- 数据：`data/gold/gold.jsonl` 的 20 篇（全在 dev），gold 不动。
- 脚本：`src/eval/evaluate.py --run-id <id>`，三档口径（严格 / 宽松 / 部分重叠）+ bootstrap 95% CI（2000 次重采样，seed=42）。
- 后处理：A2/A3/A4 一律走同一份 `postprocess.py`，报告「默认」与「`--drop-low-evidence`」两种设置。
- 比较方式：**配对**比较——同一批 20 篇上逐篇算 F1，再做配对 bootstrap，给「差值」的 CI，而不是只报两列点估计。
- 额外报一张「错误类型迁移表」：A1 vs A3 的 `domain_range` / `relation` / `schema` / 过度抽取（FP 数按类型）变化，用来回答「微调到底修好了什么」。

## 5 消融（都在 20 篇上，成本极低）

| 编号 | 变量 | 目的 |
|---|---|---|
| E1 | 训练样本 60 vs 150 条 | 数据量敏感性（小样本天花板在哪） |
| E2 | max_seq_len 1024 vs 2048 | 截断偏差有多大 |
| E3 | 有/无证据一致性过滤 | 与主实验消融对齐 |
| E4 | 3B 提示词（A2）vs 3B 微调（A3） | 同规模下「改提示」vs「改参数」 |

## 6 时间与算力预算

| 步骤 | 预计 | 阻塞项 |
|---|---|---|
| 装 torch/transformers/peft/bitsandbytes（cu124） | 20–40 min | 磁盘 3–4 GB |
| 下载 Qwen2.5-3B-Instruct（hf-mirror） | 20–60 min（6.2 GB，取决于带宽） | 需 `HF_ENDPOINT` |
| train 100 篇弱标注生成 | 100–120 min（后台） | GPU 独占 |
| 数据校验与构造 | 10 min | 无 |
| QLoRA 训练（约 150 条 × 4 epoch） | 40–90 min | GPU |
| 20 篇推理（3B 底座 + 适配器） | 15–25 min | GPU |
| 评测 + 图表 + 文档更新 | 40 min | 无 |
| **合计** | **约 5–7 小时机器时间** | |

建议顺序：**先跑第 3 行（弱标注，纯 Ollama、不依赖 torch 环境）**，同时装依赖、下模型，三件事并行。

## 7 风险与降级路径（写论文时按实际情况落地）

| 风险 | 触发信号 | 处理 |
|---|---|---|
| 依赖装不上 | bitsandbytes 在 Windows 导入失败 | 退到 fp16 + LoRA（3B fp16 训练约 7 GB，需先关桌面程序腾显存）；仍失败则只报 A2，微调写入局限 |
| 下载超时 | hf-mirror 也慢于 1 MB/s | 改 `modelscope` 下载 Qwen2.5-3B，或退到 Qwen2.5-1.5B（3.1 GB） |
| OOM | CUDA out of memory | seq_len 1024 + `grad_accum 16` + 关 checkpointing 之外的所有缓存 |
| 只学会格式、指标不涨 | A3 实体 F1 与 A2 差 < 0.02 且 JSON 合法率显著上升 | 这就是**结论本身**：小样本微调换来的是合规率而非抽取能力。照实写，配 E1 数据量曲线 |
| 指标倒退 | A3 明显低于 A2 | 归因：弱标注放大了 A1 的过度抽取（`affected_by`/`occurred_at` 偏多），列出品类迁移表 |

## 9 与你给的那份进度清单的对应关系

| 他们做了 | 我们怎么做 | 差异原因 |
|---|---|---|
| PDF 整理 + 197 训练 / 26 验证 | 直接复用 train 100 篇弱标注（约 100–150 条） | 我们不重标，避免「自己标自己评」的循环 |
| 三模型 LoRA（Qwen2.5-7B / VL-7B / InternVL3.5-8B） | 单模型 3B（可选 7B） | 6 GB 显存 + 24 GB 磁盘，跑三个不现实；横评会变成「跑不动」而不是「有结论」 |
| VL 模型读页面图 | **不做** | 本机 `data/pdf` 里 US 报告一份都没有（只有 UK 2 份、CN 4 份），没有输入就没有实验 |
| 语义相似度评分 | 沿用三档 span 匹配 + bootstrap CI | 抽取任务的正确性必须落在实体/关系粒度上，相似度只能辅助 |
| 阈值扫描 | 保留（证据一致性阈值），5 折 CV 定阈值 | 已验证 0.85 非过拟合点 |
| 分块推理 65 chunks | 用分节截断（原因段 40% 预算），不做 chunk 级划分 | 划分必须按文档/事故，chunk 只是渲染单位，避免泄漏 |

## 10 换机器交接清单（2026-11-05 本机已停）

**本机停在哪**：弱标注生成（`runner.py --split train --run-id sft_weaktrain`）刚启动就停了，`data/runs/sft_weaktrain/raw` 只有 1 篇残件，**换机器后重跑即可**（`--overwrite` 或换 run-id）。依赖包与模型权重一个都没装、没下，磁盘没动。

**新机器要满足的底线**：CUDA 驱动 ≥ 535（能跑 cu121/cu124）、显存 ≥ 8 GB（想跑 7B QLoRA 就 ≥ 12 GB）、磁盘 ≥ 40 GB、Python 3.10–3.12。

**上手顺序（全部命令都在仓库根目录）**：

```bash
git clone https://github.com/LGY873/ship-collision-kg.git
cd ship-collision-kg
python -m venv .venv && .venv\Scripts\activate      # Linux/macOS 用 source .venv/bin/activate
pip install -r requirements.txt
python tools/check_env.py && python tools/smoke_test.py   # 先证明数据与代码没问题
```

```powershell
# 1) 弱标注（纯 Ollama，先装 ollama 并 pull qwen2.5:7b-instruct）
python src/llm/runner.py --strategy p1 --model qwen2.5:7b-instruct `
  --split train --corpus data/corpus/corpus_us_seed_split.jsonl `
  --run-id sft_weaktrain --max-tokens 4096

# 2) 训练栈（显存大就装 cu124，小就装 CPU 版做数据侧调试）
pip install torch --index-url https://download.pytorch.org/whl/cu124
pip install transformers peft bitsandbytes datasets accelerate trl sentencepiece

# 3) 下基座模型（HF 直连不通时用镜像）
$env:HF_ENDPOINT = "https://hf-mirror.com"
```

**到新机器后可改的三个量**：显存 ≥ 12 GB 就把基座从 3B 换成 7B、`max_seq_len` 从 2048 提到 3072、可以把 A4（7B QLoRA）当成正式臂而不是可选项；磁盘宽裕时再考虑 VL 线（前提仍是要有页面图数据集，本仓库没有 US PDF）。
