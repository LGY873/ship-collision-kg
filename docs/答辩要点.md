# 答辩要点（一页纸）

## 一句话讲清楚做了什么

把 NTSB 公开的船舶碰撞事故调查报告，用本地 7B 大模型自动抽成「实体—关系」三元组，建成可查询的知识图谱，并给出严格的量化评测。

## 三个数字（记住这三个就够）

| 指标 | 数值 | 口径 |
|---|---|---|
| 实体 F1 | **0.784** | 严格匹配，20 篇人工标注 |
| 关系 F1 | **0.555** | 严格匹配 |
| 关系 F1（证据过滤后） | **0.597** | 开关默认关，作消融项 |

## 技术路线（答辩时按这条线讲）

```
285 起事故种子表
   → 599 份报告解析（pdfplumber + PyMuPDF）
   → 清洗 + 分节（原因段优先 40% 预算）+ 句末截断 12000 字符
   → 提示词（本体约束 p1）+ qwen2.5:7b-instruct 本地推理
   → JSON 容错解析 + schema/本体校验 + 挂载修复
   → 三元组 → 节点合并（IMO/事故号/姓名）+ 属性回填
   → 图谱（242 节点 / 254 边，33 篇）
   → 三档匹配口径评测 + bootstrap 置信区间
```

## 四个必须能答上来的问题

**Q1：为什么用大模型而不是训练专门的抽取模型？**
三个理由：标注成本（人工标 149 实体 104 关系已是极限，训练专用模型要上千篇）、算力条件（本科环境单卡 6 GB，训不动 BERT-CRF）、迁移性（换一批报告只需改提示词和本体，不用重训）。代价是输出不稳定，必须靠后处理与校验兜住 —— 这也是本文工程部分的主体。

**Q2：关系 F1 只有 0.555，是不是太低了？**
低，但原因清楚，且已定位到三类可控因素：
1. 输入截断（原始正文中位数 20460 字符，只用了前 12000）—— 召回上不去，Ship 类 7 个漏抽全部发生在被截掉的段落；
2. 过度抽取（Environment 精确率 0.538、Equipment 0.389）—— 模型把「凡提到天气/设备就抽一条」执行得过于彻底；
3. 本体与标注不一致 —— 本体 12 个关系，标注只用了 10 个，`involves_ship` 从未被标注使用，导致模型「语义正确」的输出被判为错误（实测 25 条 domain_range 违规都是这一类）。
换成完整原文 + 两阶段抽取，这两项都能改善；这属于工作量而不是方法问题。

**Q3：p2 少样本为什么比 p1 本体约束还差？这不是反常吗？**
不反常，而且这是本文最有价值的发现之一。第一轮 p2 的实体 F1 只有 0.377（p1 是 0.784）。逐项排查发现两条示例的类型配比是 Ship 6 / Person 3 / Organization 3 / Environment 3 / Accident 2 / Consequence 2，**Equipment 为 0**。模型在少样本条件下会强烈模仿示例的类型分布，于是把「设备」这一整类略过，连带紧耦合的 Consequence 也崩了。补一条以设备为主的示例（`us_DCA15LM030`）后重跑：Equipment 从 0 个回到 18 个，实体 F1 0.377 → 0.489、关系 F1 0.080 → 0.181，但仍低于 p1 的 0.784 / 0.555。
低于 p1 的原因也说清楚了：三条示例把提示词撑到约 4.5 万字符（约 1.1 万 token），加上 1.2 万字符正文已经逼近 16k 上下文上限，7B 模型在长上下文下对本体的遵守程度下降。**所以本机条件下的结论是 p1 更优，而不是「示例总是更好」。**
（可讲的细节：第一次重跑 3 例版结果与 2 例版逐位相同，最后查出是 `build_prompt.py` 的 `load_examples()` 默认 `max_n=2`，第三条示例压根没进提示词——这类实验必须先核验提示词内容。）
结论：**示例的类型分布本身就是一种隐式约束，没设计的示例会把模型校准到偏差分布上。** 这比「加示例总是更好」这样的常识更值得写进论文。

**Q4：20 篇标注是你自己标的，模型输出的基础上改的，指标可信吗？**
不完全可信，我在论文 6.8 节把它列为第一条局限。缓解手段有三个：一是三档口径（严格/宽松/部分重叠）把「写法差异」与「真抽错」分开，读者能看到误差来源；二是 bootstrap 置信区间，20 篇重采样下 CI 宽度约 ±0.1，本身就说明了样本量的限制；三是证据一致性过滤的阈值做了 5 折交叉验证（CV 均值 0.586，σ 0.056），证明不是调参调出来的。
如果要更严谨，需要 3 人独立标注 + Kappa 一致性检验，这是后续工作。

## 可能被追问的三个细节

- **分节预算为什么是 40/30/30/20/10？** 按「信息密度」排的：原因段几乎每条都是关系，事实段实体最密但噪声多，所以原因给最高权重。这个配比没做网格搜索，属于经验值，论文里作为局限说明。
- **节点合并的 Person 用什么键？** 用姓名，不用 role。早期用 role 导致所有「船长」被合并成一个节点，图上 Person 只有 1 个；修正后是 34 个。这是本文「属性提升」部分最典型的一个 bug。
- **Neo4j 为什么没跑起来？** 本机未安装/未启动（7687、7474 均未监听），所以写了等价的内存查询实现 `tools/kg_queries_local.py`，8 条查询与 Cypher 版一一对应，结论一致。Cypher 脚本已随仓库提供，装上 Neo4j 即可执行。
